# Commit Messages

Follow the [Conventional Commits](https://www.conventionalcommits.org/en/v1.0.0/) specification when creating commits.

## Prerequisites

### 1. Check the current branch

```bash
git branch --show-current
```

**If you're on `main`, `master`, `production` or `dev`, you MUST create a feature branch first** — unless the user explicitly asked to commit to main. Do not ask for confirmation; default to creating the branch.

```bash
git checkout -b <type>/<short-description>
```

Branch naming follows `<type>/<short-description>`, matching the commit type (e.g., `feat/add-user-auth`, `fix/null-pointer-error`, `refactor/extract-validation`).

### 2. Review what will be staged

```bash
git status
git diff --staged
```

Stage intentional changes only. Do not blindly `git add .` unless all changes belong to this commit. If changes span multiple concerns, split into separate commits.

## Format

```
<type>(<scope>): <subject>

<body>

<footer>
```

The header is required. Scope is optional. All lines must stay under 100 characters.

## Commit Types

| Type | Purpose | SemVer impact |
|------|---------|---------------|
| `feat` | New feature | Minor |
| `fix` | Bug fix | Patch |
| `refactor` | Code restructuring (no behavior change) | None |
| `perf` | Performance improvement | Patch |
| `docs` | Documentation only | None |
| `test` | Test additions or corrections | None |
| `build` | Build system or dependencies | None |
| `ci` | CI/CD configuration | None |
| `chore` | Maintenance tasks | None |
| `style` | Code formatting (no logic change) | None |
| `revert` | Reverts a previous commit | Patch |

## Subject Line Rules

- Use imperative, present tense: "Add feature" not "Added feature"
- Capitalize the first letter
- No period at the end
- Maximum 70 characters

## Body Guidelines

- Explain **why** and **what**, not how
- Use imperative mood and present tense
- Include motivation for the change
- Contrast with previous behavior when relevant

## Footer: Issue References

Reference issues in the footer using these patterns:

```
Fixes AB#1234
Refs AB#123
```

- `Fixes` closes the issue when merged
- `Refs` links without closing

## AI-Generated Changes

When changes were generated by a coding agent, include the appropriate Co-Authored-By attribution in the commit footer:

```
# GitHub Copilot
Co-authored-by: Copilot <223556219+Copilot@users.noreply.github.com>

# Claude / Claude Code
Co-Authored-By: Claude <noreply@anthropic.com>
```

This is the only indicator of AI involvement that should appear in commits. Do not add phrases like "Generated by AI", "Written with Claude", or similar markers anywhere in the commit message.

## Running the Commit

Use `-m` for simple messages. For multi-line messages, pass multiple `-m` flags (each becomes a paragraph):

```bash
git commit -m "type(scope): Subject" -m "Body paragraph." -m "Footer: Fixes AB#1234"
```

## Non-Obvious Formats

### Breaking change — requires both `!` on the header AND a `BREAKING CHANGE:` footer

```
feat(api)!: Remove deprecated v1 endpoints

Remove all v1 API endpoints that were deprecated in version 23.1.
Clients should migrate to v2 endpoints.

BREAKING CHANGE: v1 endpoints no longer available
Fixes AB#1234
```

### Revert — references the original commit SHA

```
revert: feat(api): Add new endpoint

This reverts commit abc123def456.

Reason: Caused performance regression in production.
```

## Principles

- Each commit should be a single, stable change
- Commits should be independently reviewable
- The repository should be in a working state after each commit
